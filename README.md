# Discord Tools: защищённая панель

Панель управления и мониторинга существующей SQLite-базы. Вход по паролю, просмотр состояний, поиск, фильтры, карточки аккаунтов, CSV без секретных токенов, журнал событий и отзыв сессий. Внешних шрифтов, JS-библиотек и сборки Node.js нет.

**Режимы:** `dashboard_api.py --with-worker` запускает панель и обработчик в одном процессе; именно этот режим использует служба `discord-dashboard`. Без флага остаётся мониторинг: загрузка и новая выгрузка отключены, сохранённые файлы доступны. Telegram доставляет уведомления и файлы, команды бота не опрашиваются. Незавершённые очереди автоматически не возобновляются.

Модуль продажи полностью удалён из исходников: интеграции TokenBuyRobot и Tskupka, фоновые задачи продажи и повторной очистки между площадками, команды Telegram, API и экран истории заявок, учёт продаж в Google Sheets. Старые сообщения бота не запускают удалённые команды. Покупки через LZT и существующая выгрузка в файл относятся к отдельным функциям и сохранены.

Старая таблица `sales` и ранее записанные статусы могут оставаться в существующей БД как архив: приложение их не возобновляет и не использует для продаж, таблица больше не создаётся. Неизвестные состояния в панели обозначены как архивные. Рабочую БД и историю Git эта доработка не удаляет.

При обновлении остановите старый процесс перед заменой файлов и удалите из установленного проекта `modules/sales.py`, `modules/google_sheets.py`, `test_sales.py`, если переносите изменения копированием поверх старого каталога. При обновлении через Git удаления применяются вместе с изменениями. После перезапуска используется код без модуля продажи; старые ключи площадок и разделы `sales` / `google_sheets` в собственной конфигурации больше не нужны.

## Что потребуется для сервера 24/7

- Linux-сервер с Python 3.11 или новее и постоянным диском. Ориентир для самой панели — 1–2 vCPU и 1–2 ГБ RAM; это начальная оценка, нагрузочные проверки не проводились.
- Актуальная SQLite-база и каталог для журналов и резервных копий. Файл в Git является старым снимком, его не следует подменять им вашу рабочую БД.
- Домен или поддомен, например `panel.example.com`, с DNS-записью на IP сервера.
- Caddy для HTTPS. Входящие порты 80 и 443 должны быть доступны; порт Flask/Waitress 5000 слушает только `127.0.0.1` и наружу не открывается.
- Пароль администратора, секрет подписи сессии и точный публичный адрес панели. Настроечный скрипт создаёт хеш пароля и случайный секрет, не выводя их в терминал.

Статический хостинг не исполняет Flask и не хранит рабочую SQLite-базу. Для этой реализации нужен постоянно работающий Python-процесс. Панель и рабочие данные должны находиться на одном сервере либо данные должны доставляться туда отдельно. Облачный туннель для постоянного адреса не требуется.

## Настройка

Разместите обновлённый проект в `/opt/discord-tools`. Создайте отдельного системного пользователя `discord-tools`, назначьте ему чтение проекта и `.env`, запись в каталог `data`. Не запускайте веб-сервис от root.

Из каталога проекта:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

Создайте `.env` на основе `.env.example` **только если файла ещё нет**. Не перезаписывайте существующие секреты. Затем:

```sh
.venv/bin/python scripts/setup_dashboard.py
```

Скрипт спросит логин, публичный адрес и пароль. Для сервера используйте `https://ваш-домен`; в `DASHBOARD_PUBLIC_URL` не должно быть пути или завершающего слеша. Хеш и ключ будут записаны в `.env` с правами 0600. Убедитесь, что `.env` принадлежит пользователю сервиса. Не подключайте `.env` через `source`: приложение само читает значения, включая символы `$` в хеше.

Обязательные переменные для панели:

| Переменная | Назначение |
| --- | --- |
| `DASHBOARD_USERNAME` | Логин; по умолчанию `admin` |
| `DASHBOARD_PASSWORD_HASH` | Хеш, созданный скриптом настройки |
| `DASHBOARD_SECRET_KEY` | Случайный секрет подписи cookie |
| `DASHBOARD_PUBLIC_URL` | Единственный разрешённый публичный адрес |

Отдельной панели не нужны LZT- или Telegram-ключи: она читает локальную БД. Зависимости `gspread` и `google-auth` больше не используются.

Для существующего Telegram-бота задайте `TELEGRAM_ALLOWED_USER_IDS=123456789,987654321`. Это **числовые ID пользователей**, не имена `@username` и не ID группы. Команды бота отключены; управление выполняется через защищённую панель. `TELEGRAM_CHAT_ID` остаётся адресом уведомлений. Для совместимости положительный ID личного чата может использоваться как единственный владелец, если явного списка нет; для группы список владельцев обязателен.

В `config.json`:

```json
{
  "database": {"path": "data/tokens.db"},
  "logging": {"level": "INFO", "file": "data/logs/pipeline.log"},
  "dashboard": {"host": "127.0.0.1", "port": 5000, "session_hours": 8}
}
```

Это минимальная конфигурация отдельной панели. Остальные разделы существующего файла можно сохранить. Пути к базе и журналу разрешаются относительно расположения `config.json`.

## Схема БД

При инициализации `Database` схема мигрирует до версии 4 автоматически. Перед первой миграцией существующей базы создаётся согласованная SQLite-копия рядом с ней: `tokens.db.backup_ДАТА`. Добавляются отсутствующие столбцы, в частности `seller_username`, создаются недостающие таблицы. ID, токены, статусы и даты существующих записей сохраняются. Повторная инициализация не создаёт повторных миграций. Более новая неизвестная версия схемы отклоняется.

Для явной миграции без запуска сервера:

```sh
.venv/bin/python migrate_database.py --config /opt/discord-tools/config.json
```

Исходный бинарный файл базы в этой доработке не изменялся: миграция выполнится только после вашего запуска. Перед обновлением рабочей установки остановите её процесс и сохраните резервную копию.

Незавершённые `new`, `validated`, `cleaning`, `cleaned` остаются в БД и видны в панели. В режиме отдельного мониторинга это последнее сохранённое состояние, а не подтверждение работающего потока. Автоматическое восстановление очередей в эту версию не входит.

## HTTPS и автозапуск

1. Замените `panel.example.com` в `deploy/Caddyfile` на домен из `DASHBOARD_PUBLIC_URL`.
2. Установите Caddy по [официальной инструкции](https://caddyserver.com/docs/install) и разместите блок конфигурации в его Caddyfile. Сохраните другие сайты, если Caddy уже используется.
3. Убедитесь, что `/opt/discord-tools/data` существует и доступен на запись пользователю `discord-tools`. Не меняйте путь к данным без одновременного обновления `ReadWritePaths` службы.
4. Для управления нужна полная конфигурация обработчика из `config.json`, включая разделы LZT, Telegram, validator и cleaner; минимальный пример выше подходит только мониторингу. Задайте ключи в `.env`. Подготовьте отдельный конфиг в доступном на запись каталоге `data`:

```sh
.venv/bin/python scripts/prepare_service_config.py
sudo chown discord-tools:discord-tools data/config.json
```

Скрипт сохраняет `${ENV}` и переводит относительные пути базы/логов в абсолютные. Существующий `data/config.json` не перезаписывается: при обновлении редактируйте его, а не создавайте заново. `.env` в корне проекта продолжает загружаться. Для атомарного сохранения переключателей сервису нужна запись в каталог конфигурации; `ReadWritePaths` уже разрешает `data`.

5. Установите службу:

```sh
sudo cp deploy/discord-dashboard.service /etc/systemd/system/discord-dashboard.service
sudo systemctl daemon-reload
sudo systemctl enable --now discord-dashboard
sudo systemctl reload caddy
```

`systemd` запускает панель вместе с обработчиком после загрузки сервера и перезапускает после ошибки. Waitress обслуживает HTTP в одном процессе с несколькими потоками; Caddy завершает HTTPS и передаёт запросы на loopback. Не запускайте несколько копий этой службы на одном порту. Сессии хранятся в памяти процесса: перезапуск сервиса завершает все входы.

Откройте `https://ваш-домен` и войдите. Пароль и домен нужно настроить **до** запуска. Если они отсутствуют, сервер откажется запускаться. Локальный `/healthz` сообщает только доступность веб-сервера; все `/api/*`, кроме начала входа, требуют авторизации.

Для просмотра ошибок службы:

```sh
sudo journalctl -u discord-dashboard -n 100 --no-pager
```

Панель читает структурированные строки из файла журнала, указанного в конфиге. В режиме мониторинга в журнал попадают события самой панели; события другого процесса появятся только если он пишет в тот же файл.

## Резервные копии и обновления

```sh
.venv/bin/python scripts/backup_database.py data/tokens.db /путь/к/резервным-копиям
```

Скрипт использует SQLite backup API, включая зафиксированные записи из WAL. Храните копии на отдельном защищённом диске, задайте собственный график и срок хранения. Для восстановления остановите процессы, работающие с БД, и восстанавливайте согласованную копию, а не произвольный набор `.db`/`-wal`/`-shm`.

Для смены пароля снова выполните скрипт настройки и перезапустите службу. Кнопка «Завершить все сессии» отзовёт текущие входы сразу. Вход ограничен 10 попытками за 5 минут с адреса и 60 попытками суммарно за это время.

В панели отсутствуют сырые токены; CSV также содержит только метаданные. Ранее добавленные в Git файлы БД и логов всё ещё остаются в истории репозитория. Новые правила `.gitignore` не удаляют опубликованные данные и не отзывают ранее раскрытые секреты.

## Локальный вариант

Для локального мониторинга можно задать `DASHBOARD_PUBLIC_URL=http://127.0.0.1:5000` и запустить `.venv/bin/python dashboard_api.py`. Для управления используйте `.venv/bin/python dashboard_api.py --with-worker`. Не запускайте одновременно отдельную панель и обработчик с панелью на одном порту. Для удалённого HTTP приложение отказывает в настройке; используйте HTTPS. `/miniapp` открывает ту же защищённую панель и требует входа, вместо прежнего незащищённого iframe.

## Проверка этой доработки

Изолированные регрессионные проверки запускаются командой `.venv/bin/python -m unittest discover -s tests -v`. Они используют временные базы и подменяют внешние вызовы; рабочие интеграции не вызываются.

Решения по cookie, CSRF и заголовкам основаны на [рекомендациях Flask](https://flask.palletsprojects.com/en/stable/web-security/); конфигурация прокси — на [документации Waitress](https://docs.pylonsproject.org/projects/waitress/en/stable/reverse-proxy.html) и [Caddy](https://caddyserver.com/docs/quick-starts/reverse-proxy).


## Надёжность выгрузки

Вкладка «Токены» хранит историю последних 100 выгрузок. Сам архив в SQLite не удаляется автоматически; более старые файлы доступны через авторизованный `/api/tokens/export/download?id=НОМЕР`. Выгрузка сохраняет файл и статусы в одной транзакции; `sent` означает, что запись включена в сохранённую выгрузку. Доставка Telegram показывается отдельно. Если процесс остановился во время доставки, её результат может остаться «не подтверждён», но файл можно скачать.

Пустой экспорт и ошибки не уничтожают ранее сохранённые файлы. При временной ошибке проверки записи остаются `ready`; их можно проверить повторно. Загрузка пропускает дубликаты и показывает количество ошибок записи, сохраняя введённый текст для повторной попытки. После остановки обработчика загрузка недоступна; для возобновления перезапустите сервис. Остановка из панели ждёт окончания активной выгрузки.

Для режима только мониторинга запускайте `dashboard_api.py` без `--with-worker`. Чтобы использовать его через systemd, задайте override `ExecStart` с очищением прежнего значения и уберите флаг; не запускайте второй процесс на том же порту.


## Прокси аккаунтов и rate limit

Все запросы аккаунтов к Discord в обработчике используют общий прокси-транспорт: первая/финальная проверка, очистка, проверка перед выгрузкой и дополнительный checker. `proxy.enabled=false`, пустой пул или недоступный закреплённый прокси блокируют запросы — прямого fallback нет. Переменные `HTTP(S)_PROXY` / `NO_PROXY` не подменяют назначение. SOCKS использует DNS на стороне прокси (`socks5h` / `socks4a`). Уведомления Telegram и обращения к LZT — отдельные сервисные интеграции, они не используют прокси Discord-аккаунтов.

Назначение постоянно и хранится в `proxy_bindings`: одна запись аккаунта (идентифицируется хешем токена) — одна нормализованная конфигурация прокси; одна конфигурация не выдаётся другой записи. Это требует отдельного прокси для каждой обрабатываемой записи, а не только для каждого одновременного потока. После выгрузки привязка сохраняется. Удаление прокси из пула не освобождает привязку: для продолжения восстановите и перепроверьте тот же прокси. Перезапуск и HTTP 429 не меняют назначения. Изменение токена создаёт новую запись, так как идентификация по Discord user ID здесь не выполняется.

Разные настройки прокси не доказывают разные выходные IP: один провайдер может выдавать общий адрес разным логинам. Проверена изоляция маршрутизации в приложении; независимые внешние IP нужно обеспечить конфигурацией провайдера. Автоматической ротации IP для обхода ограничений нет.

Вкладка **«Сеть и лимиты»** показывает закрепления (ID записи и безопасный отпечаток вместо токена), доступность, активный этап, cooldown, число запросов/429 за 1 и 5 минут, долю 429, отдельные показатели очистки, сетевые ошибки и последние события с областью `user/global/shared`. Учётные данные прокси не показываются. Число секунд — сумма задержек, назначенных ответами Discord, а не фактический простой всего приложения. Метрики хранятся в памяти с запуска; 429 также пишутся в обычный журнал. При переполнении окна отображается предупреждение о неполных данных.

Обработка 429 следует `Retry-After` / `retry_after`; учтены не-JSON ответы и исчерпание попыток. Cooldown сохраняется между запросами и этапами одного аккаунта; общий ресурс с `shared` ограничивает обращения других аккаунтов к этому же маршруту. Потоки не увеличиваются автоматически. При повторяющихся 429 уменьшите нагрузку и сравните следующее окно наблюдений; отсутствие 429 на небольшой выборке не означает наличие запаса. Основание: [официальная документация Discord о rate limits](https://docs.discord.com/developers/topics/rate-limits).

Функции выбора сообщений, удаления и закрытия чатов не изменены; неизменность исходного текста двух функций очистки проверяется SHA-256 в тестах. При исчерпанных сетевых попытках внешний обработчик возвращает запись в очередь вместо отметки об успешной очистке.
