# Discord Tools: защищённая панель

Панель мониторинга существующей SQLite-базы. Вход по паролю, просмотр состояний, поиск, фильтры, карточки аккаунтов, CSV без секретных токенов, журнал событий и отзыв сессий. Внешних шрифтов, JS-библиотек и сборки Node.js нет.

**Граница этой версии:** отдельный запуск панели не запускает обработку аккаунтов, проверки или очистку. Незавершённые состояния показываются из БД, но очереди автоматически не возобновляются. Это защищённая панель мониторинга.

Модуль продажи полностью удалён из исходников: интеграции TokenBuyRobot и Tskupka, фоновые задачи продажи и повторной очистки между площадками, команды Telegram, API и экран истории заявок, учёт продаж в Google Sheets. Старые сообщения бота не запускают удалённые команды. Покупки через LZT и существующая выгрузка в файл относятся к отдельным функциям и сохранены.

Старая таблица `sales` и ранее записанные статусы могут оставаться в существующей БД как архив: приложение их не возобновляет и не использует для продаж, таблица больше не создаётся. Неизвестные состояния в панели обозначены как архивные. Рабочую БД и историю Git эта доработка не удаляет.

При обновлении остановите старый процесс перед заменой файлов и удалите из установленного проекта `modules/sales.py`, `modules/google_sheets.py`, `test_sales.py`, если переносите изменения копированием поверх старого каталога. При обновлении через Git удаления применяются вместе с изменениями. После перезапуска используется код без модуля продажи; старые ключи площадок и разделы `sales` / `google_sheets` в собственной конфигурации больше не нужны.

## Что потребуется для сервера 24/7

- Linux-сервер с Python 3.11 или новее и постоянным диском. Ориентир для самой панели — 1–2 vCPU и 1–2 ГБ RAM; это начальная оценка, нагрузочные проверки не проводились.
- Актуальная SQLite-база и каталог для журналов и резервных копий. Файл в Git является старым снимком, его не следует подменять им вашу рабочую БД.
- Домен или поддомен, например `panel.example.com`, с DNS-записью на IP сервера.
- Caddy для HTTPS. Входящие порты 80 и 443 должны быть доступны; порт Flask/Waitress 5000 слушает только `127.0.0.1` и наружу не открывается.
- Пароль администратора, секрет подписи сессии и точный публичный адрес панели. Настроечный скрипт создаёт хеш пароля и случайный секрет, не выводя их в терминал.

Статический хостинг не исполняет Flask и не хранит рабочую SQLite-базу. Для этой реализации нужен постоянно работающий Python-процесс. Панель и рабочие данные должны находиться на одном сервере либо данные должны доставляться туда отдельно. Облачный туннель для постоянного адреса не требуется.

## Настройка

Разместите обновлённый проект в `/opt/discord-tools`. Создайте отдельного системного пользователя `discord-tools`, назначьте ему чтение проекта и `.env`, запись в каталог `data`. Не запускайте веб-сервис от root.

Из каталога проекта:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

Создайте `.env` на основе `.env.example` **только если файла ещё нет**. Не перезаписывайте существующие секреты. Затем:

```sh
.venv/bin/python scripts/setup_dashboard.py
```

Скрипт спросит логин, публичный адрес и пароль. Для сервера используйте `https://ваш-домен`; в `DASHBOARD_PUBLIC_URL` не должно быть пути или завершающего слеша. Хеш и ключ будут записаны в `.env` с правами 0600. Убедитесь, что `.env` принадлежит пользователю сервиса. Не подключайте `.env` через `source`: приложение само читает значения, включая символы `$` в хеше.

Обязательные переменные для панели:

| Переменная | Назначение |
| --- | --- |
| `DASHBOARD_USERNAME` | Логин; по умолчанию `admin` |
| `DASHBOARD_PASSWORD_HASH` | Хеш, созданный скриптом настройки |
| `DASHBOARD_SECRET_KEY` | Случайный секрет подписи cookie |
| `DASHBOARD_PUBLIC_URL` | Единственный разрешённый публичный адрес |

Отдельной панели не нужны LZT- или Telegram-ключи: она читает локальную БД. Зависимости `gspread` и `google-auth` больше не используются.

Для существующего Telegram-бота задайте `TELEGRAM_ALLOWED_USER_IDS=123456789,987654321`. Это **числовые ID пользователей**, не имена `@username` и не ID группы. Команды принимаются только в личном чате с указанным владельцем. `TELEGRAM_CHAT_ID` остаётся адресом уведомлений. Для совместимости положительный ID личного чата может использоваться как единственный владелец, если явного списка нет; для группы список владельцев обязателен.

В `config.json`:

```json
{
  "database": {"path": "data/tokens.db"},
  "logging": {"level": "INFO", "file": "data/logs/pipeline.log"},
  "dashboard": {"host": "127.0.0.1", "port": 5000, "session_hours": 8}
}
```

Это минимальная конфигурация отдельной панели. Остальные разделы существующего файла можно сохранить. Пути к базе и журналу разрешаются относительно расположения `config.json`.

## Схема БД

При инициализации `Database` схема мигрирует до версии 1 автоматически. Перед первой миграцией существующей базы создаётся согласованная SQLite-копия рядом с ней: `tokens.db.backup_ДАТА`. Добавляются отсутствующие столбцы, в частности `seller_username`, создаются недостающие таблицы. ID, токены, статусы и даты существующих записей сохраняются. Повторная инициализация не создаёт повторных миграций. Более новая неизвестная версия схемы отклоняется.

Для явной миграции без запуска сервера:

```sh
.venv/bin/python migrate_database.py --config /opt/discord-tools/config.json
```

Исходный бинарный файл базы в этой доработке не изменялся: миграция выполнится только после вашего запуска. Перед обновлением рабочей установки остановите её процесс и сохраните резервную копию.

Незавершённые `new`, `validated`, `cleaning`, `cleaned` остаются в БД и видны в панели. В режиме отдельного мониторинга это последнее сохранённое состояние, а не подтверждение работающего потока. Автоматическое восстановление очередей в эту версию не входит.

## HTTPS и автозапуск

1. Замените `panel.example.com` в `deploy/Caddyfile` на домен из `DASHBOARD_PUBLIC_URL`.
2. Установите Caddy по [официальной инструкции](https://caddyserver.com/docs/install) и разместите блок конфигурации в его Caddyfile. Сохраните другие сайты, если Caddy уже используется.
3. Убедитесь, что `/opt/discord-tools/data` существует и доступен на запись пользователю `discord-tools`. Не меняйте путь к данным без одновременного обновления `ReadWritePaths` службы.
4. Установите службу:

```sh
sudo cp deploy/discord-dashboard.service /etc/systemd/system/discord-dashboard.service
sudo systemctl daemon-reload
sudo systemctl enable --now discord-dashboard
sudo systemctl reload caddy
```

`systemd` запускает панель после загрузки сервера и перезапускает после ошибки. Waitress обслуживает HTTP в одном процессе с несколькими потоками; Caddy завершает HTTPS и передаёт запросы на loopback. Не запускайте несколько копий этой службы на одном порту. Сессии хранятся в памяти процесса: перезапуск сервиса завершает все входы.

Откройте `https://ваш-домен` и войдите. Пароль и домен нужно настроить **до** запуска. Если они отсутствуют, сервер откажется запускаться. Локальный `/healthz` сообщает только доступность веб-сервера; все `/api/*`, кроме начала входа, требуют авторизации.

Для просмотра ошибок службы:

```sh
sudo journalctl -u discord-dashboard -n 100 --no-pager
```

Панель читает структурированные строки из файла журнала, указанного в конфиге. В режиме мониторинга в журнал попадают события самой панели; события другого процесса появятся только если он пишет в тот же файл.

## Резервные копии и обновления

```sh
.venv/bin/python scripts/backup_database.py data/tokens.db /путь/к/резервным-копиям
```

Скрипт использует SQLite backup API, включая зафиксированные записи из WAL. Храните копии на отдельном защищённом диске, задайте собственный график и срок хранения. Для восстановления остановите процессы, работающие с БД, и восстанавливайте согласованную копию, а не произвольный набор `.db`/`-wal`/`-shm`.

Для смены пароля снова выполните скрипт настройки и перезапустите службу. Кнопка «Завершить все сессии» отзовёт текущие входы сразу. Вход ограничен 10 попытками за 5 минут с адреса и 60 попытками суммарно за это время.

В панели отсутствуют сырые токены; CSV также содержит только метаданные. Ранее добавленные в Git файлы БД и логов всё ещё остаются в истории репозитория. Новые правила `.gitignore` не удаляют опубликованные данные и не отзывают ранее раскрытые секреты.

## Локальный вариант

Для локальной работы можно задать `DASHBOARD_PUBLIC_URL=http://127.0.0.1:5000` и запустить `.venv/bin/python dashboard_api.py`. Для удалённого HTTP приложение отказывает в настройке; используйте HTTPS. `/miniapp` открывает ту же защищённую панель и требует входа, вместо прежнего незащищённого iframe.

## Проверка этой доработки

По просьбе пользователя приложение, миграции и тесты не запускались. Выполнен только статический разбор исходников. Работу входа, миграции на копии рабочей БД и отображение в браузерах нужно проверить перед рабочим развёртыванием.

Решения по cookie, CSRF и заголовкам основаны на [рекомендациях Flask](https://flask.palletsprojects.com/en/stable/web-security/); конфигурация прокси — на [документации Waitress](https://docs.pylonsproject.org/projects/waitress/en/stable/reverse-proxy.html) и [Caddy](https://caddyserver.com/docs/quick-starts/reverse-proxy).
